## 1. 改了什么

四处。前三处是内核 / 文件系统代码，第四处是测试仪器。

### 1.1 §17 `symlink()` 的存在性检查跟随了末级符号链接

| | |
|---|---|
| 文件 | `_dbfs2_alien/vendor/vfscore-patched/src/path.rs` |
| 函数 | `VfsPath::symlink()` |
| 改动 | `self.open(None)` → `self.open_nofollow(None)`，1 行 |

原代码用一个会**跟随**末级符号链接的打开操作来探测「newpath 是否已存在」。POSIX 规定
`symlink(2)` 在 newpath 已存在时返回 `EEXIST`，且从不解析 newpath 的末级分量。

修复前实测（DBFS2 臂，内核 `64cb4fb7`，探针 `tests/third_party/runner/probe/rc16.sh`）：

| new 的形态 | 修复前返回 | POSIX 要求 |
|---|---|---|
| 普通文件 | `EEXIST` | `EEXIST` ✓ |
| 目录 | `EEXIST` | `EEXIST` ✓ |
| FIFO | `EEXIST` | `EEXIST` ✓ |
| 有效符号链接 | `EEXIST` | `EEXIST` ✓ |
| **悬空符号链接** | **0**（inode 11→12，原链接被就地替换） | `EEXIST` ✗ |
| **自环符号链接** | **`ELOOP`** | `EEXIST` ✗ |

前四种本来就对，出错的只有悬空和成环两种——与「跟随语义」逐条对得上。

修复后（内核 `8571bfe1`，同一探针）：六种形态全部 `EEXIST`，且探测前后 inode 号不变。

对应测试目录 `symlink/`：修复前 `ok 82 / not ok 13` → 修复后 `ok 85 / not ok 10`，两次的断言总数都是 95。

（这两组数字来自同一版测试仪器——都在 §1.4 的补丁**之前**跑，用例组相同，所以可比。
不过它只能说明「净增 3 条」，不能说明「§17 解决了全部 13 条失败」：剩下 10 条里有一部分是
测试名撞名造成的假失败，见 §1.4。§17 本身的直接证据是上面的 rc16 探针。）

### 1.2 §19 `rename(x, x)` 返回 `EIO` 且 `nlink` 泄漏

| | |
|---|---|
| 文件 | `_dbfs2_alien/dbfs2/src/inode.rs` |
| 函数 | `dbfs_common_rename()` |
| 改动 | 加 `if new_number == Some(old_number) { return Ok(()); }`，3 行 |

POSIX：old 与 new 解析到同一个目录项、或同一个文件的多个硬链接时，`rename` 应当返回成功且不做任何事。

修复前实测（探针 `probe/rc17.sh`）：

| 用例 | 修复前 |
|---|---|
| `rename(x, x)`，x 是普通文件 | `EIO` |
| `rename(x, x)`，x 是目录 | `EIO` |
| `rename(x, x)`，x 是符号链接 | `EIO` |
| `rename(f, f)` / `rename(f, ./f)` / `rename(f, ../Q/f)` | 全部 `EIO`（三种写法都指向同一条目） |
| x 与 x 是同一 inode 的两个硬链接 | 返回 0，但 H1 消失、H2 的 `nlink` 由 2 变 1 |

修复后：以上全部返回 `0`，且 `(类型, inode, mode, nlink, size)` 五项不变。

判等放在 DBFS2 层而不是 vfscore 的 `rename_to()` 里，原因是这个适配层**没有 dentry 缓存**
（`DbfsDentry::find` 恒返回 `None`，dentry 每次现造），`Arc::ptr_eq` 判身份在这里恒为假；
`dbfs_common_rename()` 拿到的两侧已经是解析后的 inode 号，是这里唯一可靠的判据。
判定位置放在两个只读事务之后、第一个写事务之前，以免改变原有的权限检查优先级。

### 1.3 §20 `rename` 末级分量为 `.` / `..` 会让内核 panic

| | |
|---|---|
| 文件 | `_dbfs2_alien/vendor/vfscore-patched/src/path.rs` |
| 函数 | `VfsPath::rename_to()` |
| 改动 | 函数开头加 4 行守卫：末级分量为 `.` 或 `..` 时直接返回 `EBUSY` |

这条不在原计划里，是在跑全量回归时发现的。修复前实测（探针 `probe/rc18.sh`，内核 `64cb4fb7`）：

1. `rename A/B/. C` 返回 **0**，且 `C` 事后 `lstat` 是目录——A/B 与 C 变成了同一个 inode 的两个名字。
2. 紧接着 `rename A/B/.. C`（目标仍是 C）触发
   `jammdb/src/bucket.rs:181 Cannot delete data from a deleted bucket`，
   内核 panic，串口打出 `!TEST FINISH!`。

后果不止是返回码不对：`r16` 全量回归时，DBFS2 臂的 `rename` 批次**三次尝试全部死在这里**，
25 个 `.t` / 4857 条断言一条都没拿到。

修复后（探针 rc18）：两次 `rename` 都返回 `EBUSY`，C 未被创建，A/B 未被改动，内核存活，panic 计数为 0。

对应测试目录 `rename/`：修复前整目录 0 断言（panic 导致）→ 修复后 `ok 4407 / not ok 450`（共 4857 条断言），
用时 1278 秒，跑到 `PJD_DIR_DONE` 正常结束。

这两组数字**不是同一口径**：修复前不是「通过率低」，而是 panic 之后整批断言一条都没拿到。
所以只能表述为「从 0 条断言恢复到 4857 条断言」，不能表述为「通过率提升了多少」。

### 1.4 §18 测试仪器：`namegen` 只有 256 种输出

这一处**只改测试环境，不是 DBFS2 的改动，不进代码提交**，单独列出以免与上面三条混淆。

| | |
|---|---|
| 文件 | `tests/third_party/pjdfstest/tests-misc.sh.upstream`（注入测试镜像的 `pjdfstest/tests/misc.sh`） |
| 改动 | `namegen` / `namegen_len` 改为「单调计数器 + PID」，用 `printf '%08x%08x%08x%08x'` 保持原有的 32 位十六进制长度 |
| 计数器落盘 | `namegen` 常被写在反引号里（子 shell），变量不跨调用保持，所以计数器必须写文件（`/tmp`，ramfs） |

根因：`subsystems/vfs/src/dev/random.rs` 里 `/dev/urandom` 的实现是 `*x = read_timer() as u8`，
只保留时钟低 8 位，全库只有 256 种内容。名字从这里取随机数，因此最多 256 种名字，
测试之间互相撞名，产生假失败。

顺带否掉一个看起来显然的修法：**换回上游的 `openssl md5` namegen 是无效的**——
MD5 是确定性函数，256 种输入仍然只有 256 种摘要。熵源不改，换哈希没用。

实测（探针 `probe/rc21.sh`，同一次 boot 内对照）：

| 采样 | distinct | 撞名率 |
|---|---:|---:|
| 旧 namegen × 60 | 46 | 23% |
| 旧 namegen × 300 | 117 | 约 61% |
| 新 namegen × 300 | 300 | 0 |
| 新 `namegen_len 255` × 20 | 20（长度均 255） | 0 |

比理论上限 256 还低，说明时序相位在连续读取间会漂移，实际可用名字空间更小。

## 2. 怎么验证的

每个缺陷都配一个独立探针脚本，放在 `tests/third_party/runner/probe/`：

| 探针 | 对应 | 内容 |
|---|---|---|
| `rc16.sh` | §17 | 6 种 newpath 形态逐一调 `symlink()`，打印 `rc`、类型、inode 变化；另有一个正例守卫（对不存在的名字建链接应成功） |
| `rc17.sh` | §19 | P 组 `rename(x,x)`（文件/目录/符号链接），Q 组三种等价写法，I 组两个硬链接；R 组是正例守卫（普通的 `rename R1 R2` 必须真的搬） |
| `rc18.sh` | §20 | 复现 `rename A/B/. C` → `rename A/B/.. C`；S 组是正例守卫，用与 A/B 无关的目录 |
| `rc21.sh` | §18 | 新旧 namegen 各采样 300 次数 distinct |
| `rc22.sh` | §22（发现，未修） | `busybox mkdir -p` 行为 |

每个探针都带**正例守卫组**。只验「错误码变对了」是不够的——那样把实现改成恒报错也能过。

运行方式：把探针注入测试镜像后在 QEMU 里执行，探针输出落到宿主机文件。

## 4. 没做的 / 没验证的

1. **四臂矩阵没有跑完**。`wb-work/run_matrix.sh`（A=FAT 修复前 / B=DBFS2 修复前 / C=FAT 修复后 / D=DBFS2 修复后）
   于 01:10 启动，01:24 后不再推进（A 停在 10/17、B 停在 11/17），进程消失。
   因此 **C 与 D 两格缺失**，`D−B` 与 `C−A` 都没有全量数据，只有上面 `r19` 两个目录的局部结果。
2. **§17 的收益面是窄的**：只影响悬空链接和成环链接两种形态，`symlink` 目录净增 3 条断言。
   总体通过率几乎不动是正常的，不代表没修好，但也不能说成大幅改善。
3. **§16 长路径失败：决定不修**。已知路径长度到 3967 B 时 `mkdir -p` 能建成功；
   4095 / 4096 B 整串一次性 syscall 则返回 `ENOENT`，
   FAT32 与 DBFS2 两臂同样失败 ⇒ 属平台层，不是 DBFS2 缺陷。机制未定性：同一条路径串，
   busybox `ls` 正常、`fstest create`（更长）返回 0、`fstest lstat` 报 `ENOENT`，所以**不能**说成「长度阈值」。
4. **§22 `busybox mkdir -p` 在 Alien 上恒失败**（`probe/rc22.sh`），已复现但未修：
   每次调用都报 `can't create directory '/'`，取证 `[ -d 多级路径 ]` 为 no，即多级目录根本没建出来；
   而同一文件系统上 `pjdfstest mkdir` 一级、二级都返回 0 且目录真实存在 ⇒ 平台层问题，不是文件系统缺能力。
   另外 `mkdir /` 返回 0（应为 `EEXIST`）。
   ⚠️ 后面跑性能测试要注意：`lmbench-fs` / `p0-bundle` 里都写 `busybox mkdir -p $MP; cd $MP`，
   如果它恒失败，workload 会落到 ramfs 上，变成「测内存」而不是「测文件系统」。跑之前先让 guest `pwd` 落盘取证。
5. **FAT32 对照臂自身的缺口**（与 DBFS2 无关）：`symlink` 返回 `ENOSYS`；`rmdir` 空目录、`mkfifo`、`mknod` 返回 `EINVAL`
   ⇒ `rename` 套件级联失败。另外 FAT 臂的 `open` 批 OOM（`subsystems/mem/src/frame.rs: alloc frame failed`），
   DBFS2 臂同一批正常。这些要在报告里单列，不能算作 DBFS2 缺陷。
6. **性能测试（lmbench / iozone）尚未开始。**
7. `Cargo.toml` 里写有「其余与上游 478afdd 逐字节一致」，本地没有上游副本可核对，
   提交前建议 clone 该 commit 对一次 `diff -r`。

## 5. 关于内核二进制与测试证据的对应关系

- 上面所有「修复后」的探针与测试数据，用的是内核 `8571bfe1…`。
- 之后按要求删除了源码里的解释性注释（只删注释，未改代码；每个文件删除前后逐个数过
  「非注释非空行」数量，均未变），重新编译得到 `d6f3d1f5…`。
- 二进制变化的原因：Rust 会把 `panic!` 的 `文件:行号` 编进产物，删注释改变了行号，所以字节不同。
- 删注释后重跑了 `rc16` 与 `rc17` 两个探针核对行为，结果与 `8571bfe1` 时一致：
  - `rc16`：A1–A6 六种形态全部 `EEXIST` 且 inode 不变；C1 正例守卫（对不存在的名字建链接）成功。
  - `rc17`：P1–P3 与 Q 组三种写法全部 `rc=0` 且五元组不变；R 组正常搬移；I 组两个硬链接名都保留。
  - 输出归档在 `tests/third_party/results/r18-prefix-probes/`。
- **如果要在报告里引用测试数据，注意数据对应的是 `8571bfe1`，与当前源码编译出的 `d6f3d1f5` 不是同一个二进制。**
  两者的源码语义相同（探针行为一致），但严格来说不是同一份产物。

§17 与 §20 改动在同一个文件，但根因不同、影响面不同（一个是 errno，一个是内核 panic），拆成两个 commit 更清楚。

§18 的 `tests-misc.sh.upstream` 属于测试仪器，如果上游不接受测试改动，单独放一个 commit 或先不提交。
